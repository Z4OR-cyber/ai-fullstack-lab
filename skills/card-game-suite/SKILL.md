# 卡牌游戏全流程开发套件

将卡牌组合对战游戏从创意概念到上线运营的完整生命周期标准化，整合四大核心模块形成闭环开发体系。

## 模块总览

| 模块 | 技能名 | 核心职责 | 阶段定位 |
|------|--------|---------|---------|
| 设计流水线 | card-game-design-pipeline | 概念→GDD→卡牌设计→系统规格→交付准备 | 创意期 |
| 开发流水线 | card-game-dev-pipeline | M1设计→M2原型→M3联调→M4测试→M5上线 | 工程期 |
| 数据验证器 | card-data-validator | 结构验证→分布验证→数值验证→规则验证 | 质量门禁 |
| 平衡测试器 | card-game-balance-tester | 模拟对战→胜率矩阵→极端分析→调优建议 | 数值验证 |

## 数据流转说明

全流程的核心数据流以**卡牌JSON数据**为枢纽，贯穿四大模块：

1. **设计流水线产出** → GDD文档 + 卡牌数据库(Markdown) + 卡牌JSON数据(结构化)
2. **数据验证器接收** → 卡牌JSON数据 → 验证结构完整性/分布合理性/数值合规性 → 输出验证报告
3. **平衡测试器接收** → 合规的卡牌JSON + 战斗配置 → 3000局AI模拟对战 → 胜率矩阵 + 调优建议
4. **调优反馈** → 根据调优建议修改卡牌数值 → 重新验证 → 重新测试 → 循环直到达标
5. **开发流水线接收** → 达标的卡牌数据 + 设计文档 → 编码实现 → 里程碑推进 → 上线

### 关键数据格式：卡牌JSON

```json
{
  "id": "CARD_001",
  "name": "焰犬",
  "faction": "fire",
  "cost": 1,
  "type": "creature",
  "rarity": "N",
  "attack": 1,
  "health": 2,
  "effects": [{"trigger": "passive", "params": {"target": "self", "type": "taunt"}}],
  "skill_text": "嘲讽"
}
```

**必填字段**：`id`, `name`, `faction`, `cost`(0-10), `type`(creature/spell/enchantment), `rarity`(N/R/SR/SSR/UR)
**条件必填**：`attack` + `health`(creature类型), `effects`(效果数组), `skill_text`(技能描述)

### 模块一：设计流水线 (card-game-design-pipeline)

将游戏创意转化为完整的设计文档体系。核心价值：标准化流程 + 可并行 + 可迭代 + 可复用。

#### 五个阶段

| 阶段 | 名称 | 输入 | 产出 |
|------|------|------|------|
| Stage 1 | GDD框架 | 游戏类型、平台、核心卖点、参考游戏 | GDD v1（14章节：概述/世界观/卡牌系统/流派/共鸣/技能树/牌组/战斗/运营/氪金/社交/路线图/技术架构） |
| Stage 2 | 卡牌设计 | GDD框架 + 平衡基准 | 各流派卡牌数据库（含技能树、combo示例、平衡分析） |
| Stage 3 | 系统规格 | 卡牌数据库 | 战斗系统规格书 + 环境卡库(30种) |
| Stage 4 | 内容填充 | 系统规格 | 迷宫事件库(30+事件/20遗物/5Boss) + 剧情文本(6章) |
| Stage 5 | 交付准备 | 全部设计产出 | 美术需求文档 + 任务看板 |

#### 核心设计基准

- **费用效率**：N=费×2, R=费×2+1, SR=费×2+2, SSR=费×2+3, UR=费×2+4（攻+命总和）
- **稀有度分布**：每流派 N×2 | R×3 | SR×3 | SSR×1 | UR×1
- **费用曲线**：1/2/2/3/3/4/4/5/6/7（每流派10张）
- **流派数量**：首发6流派，每赛季可新增
- **技能树**：5节点(Lv3/6/9/12/15)×二选一分支，Lv15觉醒

#### 并行设计策略

- 每流派独立设计，每2流派为一组派发子Agent（共享平衡框架）
- 跨流派共鸣卡在所有流派完成后统一设计
- Stage 3-5的多个任务可并行执行

#### 产出文件清单

| 文件 | 内容 | 阶段 |
|------|------|------|
| GDD_v1.md | 完整游戏设计文档(14章) | Stage 1 |
| 卡牌数据库_流派A_B.md | 2流派各10张+技能树 | Stage 2 |
| 卡牌数据库_流派C_D.md | 2流派各10张+技能树 | Stage 2 |
| 卡牌数据库_流派E_F.md | 2流派各10张+技能树 | Stage 2 |
| 战斗系统规格书.md | 完整战斗规则 | Stage 3 |
| 环境卡库.md | 30种环境效果 | Stage 3 |
| 迷宫事件库.md | 事件+遗物+Boss | Stage 4 |
| 剧情文本_v1.md | 6章对话文本 | Stage 4 |
| 美术需求文档.md | 风格+规范+清单 | Stage 5 |
| 任务看板.md | 分工+依赖+协作 | Stage 5 |

### 模块二：数据验证器 (card-data-validator)

验证卡牌JSON数据是否符合设计规范，作为设计→开发之间的**质量门禁**。

#### 验证流程

```
读取卡牌数据 → 结构验证 → 分布验证 → 数值验证 → 规则验证 → 输出报告
```

#### 验证规则分级

| 级别 | 检查项 | 处理方式 |
|------|--------|---------|
| **错误级** | 重复ID、缺少必填字段、费用超范围(0-10)、生物卡缺属性、稀有度/流派非法枚举 | 必须修复 |
| **警告级** | 流派卡数偏差>20%、费用曲线断层、属性偏离曲线±30%、UR占比>10%、同名>2张 | 建议修复 |
| **信息级** | 空效果(白板)、技能描述>100字符、费用=0的卡牌 | 仅供参考 |

#### 费用曲线参考表

| 费用 | 属性总和下限 | 属性总和上限 | 参考均值 |
|------|------------|------------|---------|
| 0 | 1 | 3 | 2 |
| 1 | 2 | 4 | 3 |
| 2 | 3 | 6 | 4.5 |
| 3 | 4 | 8 | 6 |
| 4 | 6 | 10 | 8 |
| 5 | 8 | 13 | 10.5 |
| 6 | 10 | 16 | 13 |
| 7+ | 13 | 22 | 17 |

> 带有强力效果的生物卡属性可适当降低(-1到-2)，纯白板生物可适当提高(+1)。

#### 自定义参数

- `factions` — 自定义流派列表（默认6流派）
- `maxDeckSize` — 牌组最大张数（默认20）
- `maxSameName` — 同名卡上限（默认2）
- `maxUR` — UR卡上限（默认1）
- `maxSSR` — SSR卡上限（默认3）
- `costRange` — 费用范围（默认0-10）

### 模块三：平衡测试器 (card-game-balance-tester)

通过大规模AI模拟对战，快速发现流派强度差异和极端对局，为数值调优提供数据支撑。

#### 工作流程

```
确认输入 → 构建合法牌组 → 两两对局模拟(3000局) → 统计分析 → 输出报告
```

#### 默认战斗配置

| 参数 | 默认值 |
|------|--------|
| 初始HP | 20 |
| 能量上限 | 10 |
| 手牌上限 | 7 |
| 场上单位上限 | 5 |
| 最大回合数 | 8 |
| 先手抽牌数 | 3 |
| 后手抽牌数 | 4 |

#### 支持的效果类型

damage(伤害), heal(治疗), shield(护盾), freeze(冻结), burn(燃烧), shock(感电), taunt(嘲讽), pierce(穿透), draw_card(抽牌), cost_reduce(减费), buff(增益), debuff(减益)

#### 支持的共鸣系统

- **同法则共鸣**：2/3/4/5张同流派分级效果
- **跨法则融合技**：预设组合触发特殊效果

#### 平衡性验收标准

| 指标 | 达标范围 | 说明 |
|------|---------|------|
| 各流派综合胜率 | 40%-60% | 核心平衡指标 |
| 先手胜率 | 50%-55% | 先后手公平性 |
| 流派间极差 | < 20% | 流派间强度差异 |
| 极端对局胜率差 | < 80% | 最极端 matchup |

#### 调优策略

- 胜率>60%的流派：nerf高费卡血量，降低生存力
- 胜率<35%的流派：buff低费卡属性，使其达到费用曲线
- 先手胜率>60%：增加后手补偿（第1回合maxEnergy+1）
- 流派极差>20%：集中调整两端流派的SR/SSR卡

### 模块四：开发流水线 (card-game-dev-pipeline)

将设计文档和验证过的卡牌数据转化为可上线的游戏产品，支持多Agent协作。

#### 里程碑阶段

| 里程碑 | 名称 | 主导角色 | 核心交付物 |
|--------|------|---------|-----------|
| M1 | 设计文档 | 设计Agent | GDD、卡牌数据库、JSON数据、校验脚本 |
| M2 | 原型开发 | 编码Agent | 项目脚手架、战斗系统原型、可玩Demo(单HTML)、平衡测试报告 |
| M3 | 联调集成 | 全体Agent | Cocos工程、网络联机、存档系统、PvE/PvP流程 |
| M4 | 测试优化 | 测试Agent | Bug回归、平衡终调、性能优化(包体3-5MB)、兼容性测试 |
| M5 | 上线发布 | 运营Agent | 微信小游戏提审、运营素材、版本管理 |

#### 多Agent协作角色

| 角色 | 职责 | 产出 |
|------|------|------|
| 设计Agent | GDD、卡牌设计、平衡调整 | 设计文档、卡牌数据、平衡补丁 |
| 编程Agent A | 核心系统、脚手架 | TypeScript代码、系统实现 |
| 编程Agent B | 战斗系统、Demo | 战斗原型、可玩Demo |
| 编程Agent C | UI、辅助系统 | UI组件、工具脚本 |
| 运营Agent | 运营策略、市场调研 | 运营方案、竞品分析 |

#### 交叉验证规范

- **触发时机**：每个里程碑结束前
- **验证范围**：代码逻辑、数据一致性、接口兼容性
- **Bug分级**：P0(阻塞→立即修复) / P1(严重→本轮修复) / P2(优化→下轮处理)
- **修复流程**：发现→分级→定位→修复→上传→交叉验证→关闭

#### 关键技术注意事项

- 共鸣效果防重复触发：使用Map记录已触发状态
- 生物卡弃牌堆时机：出牌不入弃牌堆，单位死亡时才放入
- unitId必须实例级：避免多场并发战斗ID冲突
- 伤害计算需传完整targetPlayerId

## 整合优势

### 1. 闭环数据流，消除断层
传统流程中设计→验证→测试→开发各环节容易脱节。本套件以**卡牌JSON数据**为统一数据载体，设计产出直接进入验证，验证通过直接进入平衡测试，测试达标直接进入开发，形成无缝闭环。

### 2. 质量门禁前置，降低返工成本
数据验证器和平衡测试器作为设计→开发之间的双重质量门禁，确保进入开发阶段的卡牌数据已通过结构合规性和数值平衡性验证，大幅减少开发后期的数值返工。

### 3. 迭代调优自动化
平衡测试器提供具体的nerf/buff建议，用户修改后可快速重新验证+重新测试，形成"测试→调优→再测试"的快速迭代循环，目标明确（胜率40%-60%、先手≤55%、极差<20%）。

### 4. 多Agent并行协作
设计流水线支持流派级并行设计，开发流水线定义了5种Agent角色分工和交叉验证规范，套件层面统一了协作接口和数据格式，支持多Agent高效协同。

### 5. 全生命周期覆盖
从创意概念（Stage 1 GDD）到上线运营（M5 发布），覆盖卡牌游戏完整生命周期。支持赛季更新、新流派扩展、平衡补丁等持续运营场景。

所有产出遵循统一命名规范和目录结构，卡牌ID全局唯一按流派分段编号，版本管理清晰。新增流派、赛季更新均有标准化流程，降低长期维护成本。

## 迭代扩展支持

### 新增流派流程
```
设计法则概念 → 定义关键词机制 → 设计10张初始卡 → 数据验证 → 平衡测试 → 跨流派combo验证 → 上线
```

### 赛季内容更新
- 新卡包30-50张（新法则或旧法则扩展）
- 新赛季法则（全局规则修改器）
- 新主线章节 + 新环境效果(+5种) + 新迷宫Boss
- 完整的验证→测试→调优→发布流程

### 平衡调整原则
- 卡牌数据修改不影响已有技能树路线
- 环境效果调整不影响基础规则
- 新流派上线前需测试与所有已有流派的交互
- 所有调整需通过数据验证器+平衡测试器双重确认

## 注意事项

1. 每个文档头部标注版本号、日期和对应GDD版本，方便追踪
2. 卡牌ID全局唯一，按流派分段编号（001-010流派A, 011-020流派B...）
3. 所有combo示例需标注总费用和总伤害，方便平衡验证
4. 美术需求文档中的AI生图prompt需具体到角色描述+法则元素+风格参考
5. 任务看板需标注任务依赖关系，避免开发阻塞
6. 数值平衡是持续过程，首版以"可接受"为目标，通过模拟对战微调
7. 平衡测试局数建议≥1000局以保证统计稳定性，<100局时结果可能不稳定
8. 先手胜率>65%时需在报告中标注并建议后手补偿机制
