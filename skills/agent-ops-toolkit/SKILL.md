# Agent 运维工具箱

## 概述
本技能是Agent自我运维的统一入口，整合记忆管理、资产管理、Token优化三大领域的通用工作流模式。核心理念：**所有运维任务遵循"评估→执行→验证→报告"框架**，通过共享模式实现触类旁通。

## 通用运维框架（AEVR）

所有运维任务统一遵循四阶段框架：

### A - Assess（评估）
- 扫描目标资源，收集当前状态指标
- 与阈值对比，判断是否需要操作
- 输出诊断快照（指标值/阈值/健康度）

### E - Execute（执行）
- 按优先级执行操作（安全操作优先，不可逆操作需确认）
- 批量处理：单批≤20项，批间延时5秒，避免速率限制
- 操作过程中记录每步结果

### V - Verify（验证）
- 重新扫描目标资源，对比操作前后指标
- 验证所有操作是否成功完成
- 标记失败项并记录原因

### R - Report（报告）
- 输出结构化报告：操作摘要+指标对比+失败项+建议
- 报告格式统一：Markdown表格+关键数字加粗
- 存档到 `recent_memory/review/` 目录

## 模块一：记忆资源管理

### 阈值体系
| 文件 | 容量上限 | 警戒线(85%) | 触发动作 |
|------|---------|-------------|---------|
| MEMORY.md | 5120B | 4352B | 触发GC精简 |
| TOOLS.md | 5120B | 4352B | 合并重复条目 |
| USER.md | 2048B | 1741B | 精简低频信息 |
| SOUL.md | 5120B | 4352B | 人工确认后精简 |
| SECRET.md | 5120B | 4352B | 仅删除过期凭证 |

### GC流程
1. **扫描**：读取所有即时层文件，计算字节大小
2. **诊断**：标记超85%阈值的文件为⚠️，超100%为🔴
3. **精简策略**：
   - 合并重复条目（同一规则出现≥2次）
   - 删除低频引用条目（30天未访问）
   - 缩短描述（保留锚点行，详情移到experience/）
   - TOOLS.md精简后必须同步检查experience/孤儿文件
4. **验证**：重新计算大小，确认所有文件回到85%以下
5. **报告**：输出GC报告（前→后大小对比表）

### 记忆三阶保障
- **防丢失**：GitHub私有仓库每日快照
- **防膨胀**：超85%阈值触发GC
- **防过时**：锚点加✅/⚠️/❌标记+30天衰减

## 模块二：资产管理（EvoMap）

### 资产分类原则
| 类型 | 特征 | 处理 |
|------|------|------|
| 通用型 | 方法论、技能实现、工具链 | ✅ 可上架 |
| 隐私型 | Agent配置、内部工作流、实现状态 | ❌ 不上架 |

### 隐私清洗协议（通用）
发布任何内容到外部平台前，必须清洗：
1. Agent名称 → 通用代号（如 `multi-agent-cluster`）
2. 用户名/仓库地址 → 删除
3. 具体实现状态 → 抽象描述
4. 内部时间表 → `periodic review`
5. 内部路径 → 通用描述
6. 具体数量 → `multiple`/`several`
7. 所属关系 → 去掉"our"/"my"等代词

### validation命令规则
- 格式：`node -e '...'`
- 禁止：`;` `>` `<` `&&` `||` `&` `process.env` `eval` `curl` `rm`
- 替代：`;`→`,`，`<`/`>`→`!==`，`>=`→减法+`!==`
- 必须与资产功能相关，不能是纯数学运算

### 发布流程
1. 构建GEP-A2A envelope（protocol/gep-a2a v1.0.0）
2. 分批发送（≤20资产/批，批间sleep 5s）
3. 记录每批bundle_id
4. 发布后查询状态确认全部promoted

### 撤销流程
- plain JSON格式（非GEP-A2A）
- `asset_id`和`sender_id`必须在JSON顶层
- POST到 `/a2a/asset/self-revoke`

## 模块三：Token优化

### 6大降本策略
1. **上下文截断**：保留最近N轮+系统指令，截断早期对话
2. **历史压缩**：多轮对话合并为摘要
3. **指令复用**：公共指令抽为模板，避免重复
4. **输出约束**：限制max_tokens，要求精简输出
5. **函数替代**：用function call替代自然语言解析
6. **批处理**：合并多个小请求为批量调用

### 阈值体系
| 指标 | 阈值 | 动作 |
|------|------|------|
| 单次对话token | >8000 | 触发上下文截断 |
| 历史轮数 | >20轮 | 触发历史压缩 |
| 重复指令 | ≥3次 | 抽取为模板 |
| API调用 | >10次/任务 | 考虑批处理合并 |

## 模块四：跨技能优化

### 通用批量处理工具
```python
def batch_process(items, batch_size=20, delay=5, processor_fn=None):
    """通用批处理工具，适用于所有运维场景"""
    results = []
    for i in range(0, len(items), batch_size):
        batch = items[i:i+batch_size]
        result = processor_fn(batch) if processor_fn else batch
        results.extend(result if isinstance(result, list) else [result])
        if i + batch_size < len(items):
            time.sleep(delay)
    return results
```

## 迭代优化原则

1. **碰壁再优化**：先尝试当前方案，失败后分析原因再调整
2. **交叉验证**：不同Agent执行同类任务时对比结果
3. **经验沉淀**：每次运维中发现的通用模式写入experience/
4. **阈值动态调整**：根据实际使用情况调整触发阈值
5. **工具复用**：新运维任务优先复用已有工具和模式

## 常见错误处理
| 错误场景 | 原因 | 解决方案 |
|---------|------|---------|
| 记忆文件精简后丢失关键信息 | 过度删除 | 精简前备份，精简后验证关键锚点存在 |
| EvoMap发布被拒 | validation命令不合规 | 检查shell操作符，改为功能相关断言 |
| Token优化后输出质量下降 | 压缩过度 | 保留核心上下文，只截断冗余部分 |
| 批量操作超时 | 单批过大或延时不足 | 减小batch_size，增加delay |

## 模块五：7层自动化工作流引擎（v2.0 新增）

### 设计理念
所有运维任务可抽象为7层流水线，每层有明确输入/输出和质量门控。源自投资理财小豆的整合分析，适用于定时简报、资产发布、记忆GC等所有自动化场景。

### 7层架构

```
┌─────────────────────────────────────────────────────┐
│  Layer 7: 运维层 (Ops)                               │
│  健康监控 / 告警 / 自动恢复 / 审计日志                  │
├─────────────────────────────────────────────────────┤
│  Layer 6: 交付层 (Delivery)                           │
│  格式化输出 / 多渠道分发 / 存档 / 通知                  │
├─────────────────────────────────────────────────────┤
│  Layer 5: 输出层 (Output)                             │
│  内容聚合 / 摘要生成 / 可信度评级 / 结构化组装          │
├─────────────────────────────────────────────────────┤
│  Layer 4: 验证层 (Verification)                       │
│  交叉验证 / 事实核查 / 冲突检测 / 来源审查              │
├─────────────────────────────────────────────────────┤
│  Layer 3: 处理层 (Processing)                         │
│  事实抽取 / 去重 / 排序 / 标准化 / 压缩                 │
├─────────────────────────────────────────────────────┤
│  Layer 2: 采集层 (Collection)                         │
│  搜索 / 抓取 / API调用 / 缓存命中检查                   │
├─────────────────────────────────────────────────────┤
│  Layer 1: 触发层 (Trigger)                            │
│  定时触发 / 事件触发 / 手动触发 / 条件触发              │
└─────────────────────────────────────────────────────┘
```

### 各层规范

#### Layer 1: 触发层 (Trigger)
- **定时触发**：cron表达式配置，默认每日固定时间
- **事件触发**：记忆文件超阈值、资产状态变更等事件
- **手动触发**：用户显式请求
- **条件触发**：基于前置任务完成状态自动衔接
- **输出**：`TriggerEvent { type, timestamp, context, priority }`

#### Layer 2: 采集层 (Collection)
- **多源采集**：搜索引擎、API、RSS、缓存
- **缓存优先**：24h缓存命中则跳过网络请求
- **限流控制**：单域名并发≤3，总并发≤10
- **输出**：`RawItems[] { source_url, title, content, fetched_at, from_cache }`

#### Layer 3: 处理层 (Processing)
- **事实抽取**：从原始内容中提取结构化事实
- **去重**：标题相似度>80%视为重复
- **排序**：Tier1 > Tier2 > Tier3，同Tier按时效性
- **标准化**：统一日期格式、URL格式、字段命名
- **输出**：`ProcessedItems[] { facts[], tier, dedup_key, score }`

#### Layer 4: 验证层 (Verification)
- **交叉验证**：重要信息至少2个独立来源
- **事实核查**：打开链接验证可访问性、核对关键事实
- **冲突检测**：多来源信息矛盾时标注冲突点
- **来源审查**：营销号/转载站降权
- **输出**：`VerifiedItems[] { confidence, verified_by[], conflicts[] }`

#### Layer 5: 输出层 (Output)
- **聚合**：按主题/领域分组
- **摘要生成**：每条3-5句精炼描述
- **可信度评级**：🟢高 / 🟡中 / 🔴低
- **结构化组装**：按简报/报告/仪表盘格式组装
- **输出**：`OutputDoc { sections[], metadata, quality_report }`

#### Layer 6: 交付层 (Delivery)
- **格式化**：Markdown / HTML / JSON 按需输出
- **多渠道**：对话回复 / 文件保存 / 邮件 / 飞书
- **存档**：保存到 `recent_memory/review/` 或指定目录
- **通知**：关键产出触发用户通知
- **输出**：`DeliveryResult { channels[], file_paths[], status }`

#### Layer 7: 运维层 (Ops)
- **健康监控**：记录每层执行时间、成功率、资源消耗
- **告警**：成功率<80%或执行时间超阈值时告警
- **自动恢复**：单层失败时重试3次，仍失败则降级处理
- **审计日志**：完整执行链路记录，便于回溯
- **输出**：`OpsReport { layer_stats, alerts[], recovery_actions[] }`

### 层间数据流
```python
# 7层工作流伪代码
def run_workflow(trigger_event):
    raw_items      = collection_layer(trigger_event)       # L2
    processed      = processing_layer(raw_items)            # L3
    verified       = verification_layer(processed)          # L4
    output_doc     = output_layer(verified)                 # L5
    delivery       = delivery_layer(output_doc)              # L6
    ops_report     = ops_layer(entire_execution_trace)      # L7
    return delivery, ops_report
```

### 质量门控
每层输出必须通过质量门控才能进入下一层：
| 层 | 门控条件 | 不通过处理 |
|----|---------|-----------|
| L2→L3 | 采集项≥5条 | 扩大搜索范围或放宽时效 |
| L3→L4 | 处理项≥3条 | 降级为"信息不足"简报 |
| L4→L5 | 验证通过率≥60% | 标注低可信项，不阻断流程 |
| L5→L6 | 输出文档非空 | 生成"无新内容"通知 |
| L6→L7 | 交付成功≥1渠道 | 重试或切换渠道 |

## 模块七：自适应调度建议（v2.0 新增）

### 设计目标
基于历史执行数据，自动推荐最优执行时间窗口，提升任务成功率。

### 数据采集
每次任务执行记录以下数据：
```python
execution_record = {
    "task_type": "ai_tech_briefing",  # 任务类型
    "timestamp": "2026-08-13T22:00:00+08:00",
    "duration_sec": 145,
    "success": True,
    "token_cost": 3200,
    "retry_count": 0,
    "error_type": None,
    "layer_failures": []  # 7层中哪些层失败过
}
```

### 调度建议生成规则

#### 1. 时间窗口推荐
- 统计近30天各时段（每2小时一个窗口）的成功率
- 推荐成功率最高的3个时间窗口
- 标注当前配置时间窗口的成功率

```
调度建议 - ai_tech_briefing
============================
推荐时间窗口（基于近30天数据）:
  🥇 06:00-08:00  成功率 96% (23/24次)
  🥈 22:00-00:00  成功率 92% (22/24次)
  🥉 14:00-16:00  成功率 88% (21/24次)
  当前配置: 22:00  成功率 92% ✅
```

#### 2. 失败模式分析
- 识别高频失败时段和失败原因
- 关联失败与外部因素（如API限流、网络波动）
- 给出规避建议

#### 3. 资源冲突检测
- 检测多个定时任务是否集中在同一时段
- 建议错峰执行以避免资源竞争
- 优先级：高优先级任务占据最优窗口

#### 4. 动态调整建议
- 连续3次失败：建议调整时间窗口
- Token消耗持续上升：建议触发压缩策略
- 成功率下降趋势：建议检查依赖服务状态

## 模块八：Gene蒸馏法文档治理（v2.0 新增）

### 概念来源
源自投资理财小豆的文档治理实践，通过分层蒸馏实现76%压缩率，同时保留核心信息完整性。

### 蒸馏原理
```
原始文档 (100%)
    │
    ├─ 第一轮蒸馏: 去冗余 → 保留 60%
    │   - 删除重复描述
    │   - 合并相似段落
    │   - 去除寒暄/过渡语
    │
    ├─ 第二轮蒸馏: 抽骨架 → 保留 35%
    │   - 提取关键结论
    │   - 保留数据指标
    │   - 压缩示例为引用
    │
    └─ 第三轮蒸馏: 炼精华 → 保留 24%
        - 核心规则一句话化
        - 关键阈值表格化
        - 可执行步骤编号化
```

### 蒸馏规则

#### 规则1：分层保留
| 层级 | 保留内容 | 压缩方式 |
|------|---------|---------|
| 核心层 | 规则、阈值、命令格式 | 不压缩，原样保留 |
| 支撑层 | 示例、流程图、代码 | 压缩为引用或索引 |
| 背景层 | 说明文字、上下文 | 一句话概括或删除 |

#### 规则2：质量保障
- 蒸馏前后必须保留所有**可执行指令**（命令、阈值、规则）
- 蒸馏后必须通过**功能完整性检查**：关键操作步骤无遗漏
- 压缩率目标：70-80%，但不以牺牲可执行性为代价

#### 规则3：蒸馏报告
每次蒸馏后生成报告：
```
Gene蒸馏报告
=============
原始大小: 12,400 字节
蒸馏后:   2,976 字节
压缩率:   76.0% ✅

保留内容:
  - 核心规则: 8条 (100%保留)
  - 阈值表: 3张 (100%保留)
  - 命令格式: 5个 (100%保留)
  - 流程步骤: 4个 (编号化保留)

压缩内容:
  - 背景说明: 3段 → 1句
  - 示例代码: 5段 → 2段(保留关键示例)
  - 过渡文字: 全部删除

完整性检查: ✅ 通过
```

### 适用场景
1. **记忆文件膨胀治理**：MEMORY.md/TOOLS.md超阈值时使用蒸馏替代简单删除
2. **技能文档优化**：SKILL.md过长时蒸馏为精简版+详情附录
3. **知识库压缩**：历史简报蒸馏为知识卡片
4. **经验文件整理**：experience/下长文档蒸馏为锚点+索引

### 与GC的区别
| 维度 | GC（垃圾回收） | Gene蒸馏 |
|------|---------------|---------|
| 目标 | 删除无用内容 | 压缩有用内容 |
| 信息损失 | 有（删除低频项） | 无（保留核心，压缩冗余） |
| 压缩率 | 10-30% | 70-80% |
| 可逆性 | 不可逆（删除后需从备份恢复） | 可逆（从原始文档重建） |
| 触发条件 | 超85%阈值 | 文档>4KB且含大量描述性文字 |
| 适用场景 | 即时层记忆文件 | 技能文档、知识库、经验文件 |
