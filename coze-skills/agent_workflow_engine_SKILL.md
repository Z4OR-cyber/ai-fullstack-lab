# Agent全流程自动化工作流引擎 v2

将多Agent实战中验证的通用模式整合为统一方法论。无论领域（金融/科技/自媒体/安全/游戏），任何自动化工作流都遵循相同的七层架构，每层有标准化的设计原则和质量保障机制。

**v2升级要点：**
- 运维层引入AEVR框架（Assess→Execute→Verify→Report）
- 交付层集成多平台发布引擎细节（GitHub API→EvoMap A2A→虾评skill_draft）
- 运维层增加自进化闭环（评估反馈→策略变异→进化追踪）
- 理论基础对接知识库概念体系（Harness Engineering / Loop Engineering / Context Engineering）
- 新增自媒体内容创作和Bug Bounty两个实战案例

## 理论基础

| 概念 | 来源 | 在引擎中的映射 |
|------|------|---------------|
| **Harness Engineering** | 翁荔《Harness Engineering for Self-Improvement》 | 七层架构本身即"缰绳"——约束和引导Agent行为的基础设施 |
| **Loop Engineering** | AI协同范式革命 | 触发→采集→处理→验证→输出→交付→运维→(回到触发)的闭环循环 |
| **Context Engineering** | 上下文工程演进 | 处理层的Token优化和Gene蒸馏，本质是上下文工程的最佳实践 |

## 七层架构

```
触发层 → 采集层 → 处理层 → 验证层 → 输出层 → 交付层 → 运维层
  ↑                                                        |
  └────────────── 自进化反馈闭环 ←─────────────────────────┘
```

### 1. 触发层 — 何时启动

**三种触发模式：**
- **定时触发**：Calendar日程 + rrule重复规则，适合周期性任务
- **事件触发**：用户需求/热点事件/异常信号，适合响应式任务
- **手动触发**：用户明确指令，适合一次性任务

**Calendar设置规范：**
- summary用动作短语（如"生成每日行情简报"）
- description是工单：任务目标+执行步骤+产出要求+脚本路径+存放目录
- dtstart避免整点（用15:35而非15:00），降低并发竞争
- time_range弹性窗口：未指定时间±30min，大致时段±10min，具体时间±5min
- rrule只设freq/interval/count/until，让系统从dtstart推导时间

### 2. 采集层 — 从哪获取数据

**多源采集原则：**
- 至少2个独立数据源
- 不同源命名差异是数据缺失的首要原因——建立别名映射表
- 别名重叠时自动去重，保留标准名

**搜索Query策略：**
- 全中文query → CSDN/知乎为主，一手来源极少
- 中英文混合query → 命中官方/权威站点
- 建议：每个方向1条中文+1条英文query

**来源质量分层：**
| 层级 | 类型 | 示例 |
|------|------|------|
| Tier 1 | 官方一手 | 官网公告/财报/论文/法规原文 |
| Tier 2 | 权威二手 | 主流媒体/行业报告 |
| Tier 3 | 聚合 | 技术博客/社区讨论 |

**工具输出落盘：**
- 搜索/抓取/工具调用的完整输出写入文件
- 对话中只传结构化摘要，不传原文

**文章抓取优先级：**
```
fetch_web → curl v2.0（双模式检测+OG回退）→ agent-browser（sessions_spawn）→ 人工复制
```

### 3. 处理层 — 如何加工

**Token优化八条：**
1. 工具输出落盘，对话只传摘要
2. 结构化输出（JSON Schema替代自然语言长文）
3. 命令链式化（短命令替代长命令）
4. Token预算意识（system prompt最短化，条件加载详情）
5. 批处理优先（多个独立小任务合并为一次LLM调用）
6. 缓存复用（相同query 24h内不重复搜索）
7. 摘要替代全文（历史上下文用摘要传递）
8. 分级调用（简单任务用便宜模型，复杂任务才用贵模型）

### 4. 验证层 — 如何确保质量

**多源交叉验证：**
- 数据采集≥2个来源，标记分歧数据
- 偏差>5%标记⚠️待验证，取中位数或多数一致值
- 跨日验证：连续2天数据一致→可信

**数据验证门禁（四级）：**
- 结构验证 → 分布验证 → 数值验证 → 规则验证
- 错误级必须修复，警告级建议修复，信息级仅供参考

### 5. 输出层 — 如何格式化

**Gene蒸馏压缩（通用输出格式）：**

```
## Keywords    ← 触发关键词（逗号分隔）
## Summary     ← 一句话目标+约束
## Strategy    ← 核心逻辑（编号列表，保留具体数据锚点）
## AVOID       ← 禁止事项（bullet list）
```

蒸馏原则：保留具体数据、决策逻辑、验证结论；砍掉模板化描述、重复说明、背景科普。实测压缩率76%-83%。

### 6. 交付层 — 如何分发

**五通道同步：**
| 通道 | 用途 | 发布方式 |
|------|------|---------|
| 项目文件空间 | 即时协作 | write_file直接写入 |
| notify推送 | 即时通知 | sessions_send/notify |
| GitHub仓库 | 版本控制 | Git Database API（6步推送） |
| EvoMap | 语义搜索共享 | GEP-A2A协议 |
| 虾评 | 技能商店 | skill_draft_create + publish |

**GitHub Git Database API 6步：**
1. GET refs/heads/main → 分支SHA
2. GET commits/{sha} → tree SHA
3. POST blobs → blob SHA（base64编码）
4. POST trees → 新tree SHA（批量≤10文件）
5. POST commits → commit SHA
6. PATCH refs/heads/main → 更新引用

**EvoMap GEP-A2A发布：**
- Gene类型：category枚举(repair/optimize/innovate/regulatory/explore)
- Capsule必须有substantive content（≥50字符）
- content中不能包含代码/shell命令（会触发prompt_injection_detected）
- asset_id = SHA256(canonical JSON with sort_keys + separators=(',',':'))

### 7. 运维层 — 如何保障可靠

**AEVR运维框架：**

| 阶段 | 名称 | 动作 |
|------|------|------|
| A | Assess（评估） | 扫描资源，收集指标，与阈值对比 |
| E | Execute（执行） | 按优先级执行，批量≤20项/批 |
| V | Verify（验证） | 重新扫描，对比前后指标 |
| R | Report（报告） | 输出结构化报告，存档 |

**记忆资源管理阈值：**
| 文件 | 上限 | 警戒线(85%) | 触发动作 |
|------|------|-------------|---------|
| MEMORY.md | 5120B | 4352B | GC精简 |
| TOOLS.md | 5120B | 4352B | 合并重复条目 |
| USER.md | 2048B | 1741B | 精简低频信息 |

**自进化闭环：**
```
评估反馈（6指标）→ 策略变异（自动调参）→ 进化追踪（历史+适应度）→ 反馈到触发层
```

**错误处理规范：**
- 先读错误信息，不盲目重试
- 同一工具同一参数最多重试1次
- 失败2次后换策略

## 全流程实战案例

### 案例1：金融行情推送
触发: Calendar每日15:35 → 采集: 多源API≥2来源 → 处理: 数据校验+三段式分析 → 验证: 偏差>5%标记 → 输出: Gene压缩<1500字节 → 交付: notify+存档 → 运维: 弹性调度+重试

### 案例2：AI科技简报
触发: Calendar每日08:00 → 采集: 15条query中英文混合 → 处理: 批处理事实抽取 → 验证: 单域名上限3条 → 输出: 5-8条简报 → 交付: notify+文件 → 运维: 搜索缓存24h

### 案例3：自媒体内容创作
触发: 用户需求/热点 → 采集: 热搜+爆款+账号诊断 → 处理: 选题→标题→文案(1+N模式) → 验证: 违禁词+爆款四要素评分 → 输出: 多平台改写 → 交付: 多平台发布 → 运维: 话题追踪+数据复盘

### 案例4：Bug Bounty全流程
触发: Calendar每日9:00 → 采集: HackerOne目标+子域名枚举 → 处理: 存活探测→分级→漏洞扫描 → 验证: 误报过滤+CVSS评级 → 输出: 标准化报告 → 交付: HackerOne提交 → 运维: 知识库更新+模板优化

### 案例5：卡牌游戏开发
触发: 用户需求 → 采集: 竞品分析+参考数据 → 处理: GDD→卡牌库→JSON(6流派) → 验证: 四级数据验证+3000局AI模拟 → 输出: 平衡卡牌数据 → 交付: 代码+小游戏提审 → 运维: 赛季更新+平衡补丁

## 设计新工作流的步骤

1. 明确目标：自动产出什么？
2. 分层设计：逐层填写七层架构
3. 识别复用：哪些层可套用已有技能/脚本？
4. 设置质量门控：验证层定义"通过"标准
5. 配置触发：Calendar + time_range弹性窗口
6. 小规模验证：手动跑1-2次确认
7. 上线运维：记录成功率，持续优化瓶颈层
